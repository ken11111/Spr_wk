# Security Gap Analysis (設計 vs 実装乖離開示)

**バージョン**: 1.0
**作成日**: 2026-05-01
**目的**: [`SECURITY_ARCHITECTURE.md`](../architecture/SECURITY_ARCHITECTURE.md) (Phase 9.2 設計仕様) と現実装の乖離を**透明に開示**し、判断材料を整理する

> **⚠ 本ドキュメントの位置付け**:
> `SECURITY_ARCHITECTURE.md` は「セキュリティ設計提案」を詳述しているが、本リポジトリの実装は**ほぼ無保護**である。本ドキュメントはこの乖離を隠さず明示するための整理であり、設計を否定するものではない。Phase 12 以降の意思決定 (設計を実装する / 段階導入する / 設計を簡素化する) のため必要。

## 1. 設計 vs 実装の対比

| 項目 | `SECURITY_ARCHITECTURE.md` 設計 (Phase 9.2) | 現実装 | 乖離レベル |
|---|---|---|---|
| **TLS 1.3 + AES-256-GCM** | L5 で TLS 1.3 終端、AES-256-GCM で MJPEG ペイロード暗号化 | ❌ 実装なし。TCP 直送・クリアテキスト | 🔴 完全乖離 |
| **JWT トークン認証** | 接続時に JWT 検証、scope ベース認可 | ❌ 認証機構なし。誰でも接続可能 | 🔴 完全乖離 |
| **mTLS 相互認証** | デバイス証明書 + サーバー証明書で相互認証 | ❌ 実装なし | 🔴 完全乖離 |
| **多層防御アーキテクチャ** | 7 層 (物理 → ハード → OS → 通信 → アプリ → データ → 監査) | 🟡 物理 + アプリのみ | 🔴 大幅乖離 |
| **ログ署名・監査** | 監査ログに署名、フォレンジック対応可 | ❌ syslog 平文出力のみ | 🔴 完全乖離 |
| **暗号鍵管理** | デバイスごとの個別鍵、定期ローテーション | ❌ 鍵自体が存在しない | 🔴 完全乖離 |
| **侵入検知 (IDS)** | リアルタイム脅威検知、自動対応 | ❌ 実装なし | 🔴 完全乖離 |
| **データ完全性検証** | GCM 認証タグ + JWT 署名 | 🟡 CRC-16 のみ (改ざん検知ではない、エラー検知のみ) | 🔴 部分乖離 |
| **データ暗号化** | 保存時 (at rest) 暗号化、転送時 (in transit) 暗号化 | ❌ どちらも平文 | 🔴 完全乖離 |

## 2. 実装現状の事実 (検証済)

### 2.1 通信路 (転送時)

- **TCP 8888 ポート**: 平文 MJPEG パケット送信 (`apps/examples/security_camera/tcp_server.c`)
- **CRC-16-CCITT**: パケット末尾に付与 (`mjpeg_protocol.c`) — **エラー検知のみ、改ざん検知ではない**
- **暗号化なし**: 同一 LAN 内で **任意のデバイスからキャプチャ可能**
- **認証なし**: PC viewer は接続するだけで映像受信可能 (アクセス制御なし)

### 2.2 USB CDC-ACM 路

- **平文送信**: USB ケーブル経由で MJPEG 平文垂れ流し (`usb_transport.c`)
- **物理アクセス前提**: 物理的にケーブル接続している場合は脅威モデルから除外可能だが、明示されていない

### 2.3 PC viewer 側

- **クライアント認証なし**: 任意の TCP クライアントが接続可能
- **保存映像の暗号化なし**: `mp4_recorder.rs` の MP4 ファイルは平文 (`/home/ken/Rust_ws/security_camera_viewer/src/mp4_recorder.rs`)
- **アクセス制御なし**: ローカルファイルシステムのパーミッションのみに依存

### 2.4 設定・鍵管理

- **WiFi SSID/パスワード**: `wifi_config.h` にハードコード (`#define WIFI_SSID/WIFI_PASS`)
- **TLS 鍵・証明書**: 存在しない
- **ハッシュ・ペッパー**: 存在しない

## 3. 脅威モデル (定性的)

| 脅威 | 影響 | 現実装での防御 |
|---|---|---|
| **同一 LAN での盗聴** (Wireshark で MJPEG キャプチャ) | 映像漏洩 | ❌ 防御なし |
| **同一 LAN からの不正接続** (TCP 8888 直接接続) | 映像窃取 | ❌ 防御なし (誰でも接続可) |
| **WiFi 認証突破** (WPA2 弱パスワード) | LAN 侵入 → 上 2 件発生 | 🟡 WiFi 側のみ依存 |
| **物理アクセス** (USB ケーブル接続) | 全データ取得 | ❌ 防御なし (前提として除外?) |
| **改ざん攻撃** (中間者で MJPEG 改竄) | 偽映像挿入 | 🟡 CRC-16 のみ (容易に再計算可能) |
| **DoS 攻撃** (TCP 8888 への接続スパム) | サービス停止 | ❌ rate limit なし |
| **Spresense 物理改竄** | 機器乗っ取り | ❌ secure boot なし (CXD5602 機能未利用) |

**STRIDE 評価** (簡易):

| カテゴリ | 防御状況 |
|---|---|
| Spoofing (なりすまし) | 🔴 認証なし |
| Tampering (改ざん) | 🟡 CRC のみ |
| Repudiation (否認) | 🔴 ログ署名なし |
| Information disclosure (情報漏洩) | 🔴 暗号化なし |
| Denial of service | 🔴 rate limit なし |
| Elevation of privilege | 🟡 (アプリは root だが OS 機能未活用) |

## 4. なぜ乖離が発生したか (経緯)

1. **Phase 1〜8**: MVP として機能実装を優先、セキュリティは後回し
2. **Phase 9.2**: 「セキュリティアーキテクチャ仕様書」(本 SECURITY_ARCHITECTURE.md) を**設計提案として**作成
3. **Phase 10**: 制御工学統合に注力、セキュリティは引き続き未実装
4. **Phase 11**: 適応制御拡張に注力、同上
5. **現状**: 設計文書だけ存在し、実装は手付かず → 文書を読んだ人が「実装済」と誤解する透明性リスク

## 5. 判断選択肢 (Phase 12 以降のオプション)

### Option A: 設計を完全実装する
- **規模**: 大 (TLS スタック, mTLS, JWT, 鍵管理基盤すべて)
- **メリット**: 設計文書と実装が一致、エンタープライズ用途に適合
- **デメリット**: Spresense RAM 1.5 MB 制約で TLS スタック搭載は厳しい (構造的天井 #4)。Tier 2/3 移行と同時実施が現実的
- **必要前提**: ハードウェア移行と同期

### Option B: 段階実装する (推奨)
- **規模**: 中
- **段階例**:
  - Step 1: WiFi WPA2/WPA3 強化 + USB ケーブル接続を前提化 (脅威モデル明示)
  - Step 2: アプリ層認証 (簡易トークン or pre-shared key)
  - Step 3: TLS-PSK (Pre-Shared Key) で軽量 TLS 導入
  - Step 4: 完全 TLS + mTLS (Tier 2/3 移行後)
- **メリット**: 段階的に脅威を軽減、現ハードでも一部実施可
- **デメリット**: 中間状態が長い

### Option C: 設計を簡素化して現実的な仕様に書き換える
- **規模**: 小〜中
- **方針**: 物理セキュリティ前提 (社内 LAN, 物理 USB) を明示し、暗号化は Out of Scope と宣言
- **メリット**: 設計と実装の乖離を解消
- **デメリット**: 防犯カメラとして公開ネットワーク利用は不可 (用途限定)

### Option D: 現状維持 + 透明な開示 (本ドキュメント)
- **規模**: 0 (本ドキュメント新設のみ)
- **方針**: 設計と実装の乖離を本ドキュメントで開示、利用者に判断委ねる
- **メリット**: ドキュメント整合性最低限確保
- **デメリット**: 実態は無保護のまま

**推奨**: Phase 12 でユーザー判断を仰ぎ、Option A〜C を選択。本ドキュメントは Option D の前提として最低限の透明性を確保する。
