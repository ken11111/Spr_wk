### 3 つの主要発見

1. **RST 拒否パターン** (§4) — 切断 #3 以降、PC からの SYN に対し GS2200M が **正常な FIN ではなく RST で応答** し続けることが pcap 解析で確定。Spresense 側 TCP スタックが内部状態を整合できない構造的問題

### 5.2 GS2200Mの状態遷移仮説

```
┌────────────────────────────────────────────────────────────────┐
│  正常状態                                                      │
│  ├── 接続受付 (accept) 可能                                   │
│  └── TCP送受信可能                                            │
└────────────────────────────────────────────────────────────────┘
          │
          │ 重複ACK / パケットロス
          ▼
┌────────────────────────────────────────────────────────────────┐
│  一時的エラー状態                                              │
│  ├── RTO再送試行                                               │
│  └── FIN送信（再送成功後も）                                   │
│                                                                 │
│  → Phase 9で対応可能: 再接続で回復                             │
└────────────────────────────────────────────────────────────────┘
          │
          │ 複数回の連続切断（4回）
          ▼
┌────────────────────────────────────────────────────────────────┐
│  ★深刻なエラー状態★                                          │
│  ├── accept()リソース枯渇                                      │
│  ├── 新規接続をRSTで拒否                                       │
│  └── 回復不可（再起動必要）                                    │
│                                                                 │
│  → Phase 9では対応不可: GS2200M再起動が必要                   │
└────────────────────────────────────────────────────────────────┘
```

### 5.3 推定原因

1. **接続リソース枯渇**
   - GS2200Mのファームウェアは、同時接続数に厳しい制限がある可能性
   - 短時間（1分以内）に4回の接続/切断サイクルが発生
   - 内部のソケットリソースが解放されずに枯渇

2. **TIME_WAIT状態の問題**
   - FINを送信した側はTIME_WAIT状態に入る
   - GS2200Mが4つの旧接続をTIME_WAITで保持
   - 新規接続用のリソースが確保できない

3. **accept()待機の失敗**
   - Spresense側でaccept()がブロック状態のまま
   - GS2200Mのネットワークスタックが異常状態
   - 全てのSYNにRSTで応答

## 7. 対策案

### 7.1 短期対策

1. **再接続間隔の追加**
   - 現状: 即座に再接続試行
   - 提案: 5-10秒の待機時間を追加
   - 目的: GS2200Mのリソース解放を待つ

2. **再接続回数制限の緩和**
   - 現状: 10回失敗でアプリ終了
   - 提案: 失敗後に待機時間を増加（バックオフ）
   - 例: 2秒 → 5秒 → 10秒 → 30秒

3. **RSTエラーの検出と対応**
   - RSTを受けた場合、より長い待機時間（30秒等）
   - accept()側のタイムアウト設定確認

### 7.2 中期対策

1. **GS2200M状態監視**
   - ソケット状態をログ出力
   - TIME_WAIT数の確認

2. **Spresense側のaccept()改善**
   - タイムアウト後のソケットクリーンアップ
   - listen()のバックログサイズ増加

### 7.3 長期対策

1. **ESP32-S3への移行**
   - より安定したTCPスタック
   - 高い同時接続処理能力

## 9. 結論

### 9.1 発見事項

1. **Phase 9の自動再接続は基本的に機能している**
   - 79分、52分の安定運転を達成
   - 通常の切断（重複ACK→FIN）からは正常回復

2. **新たな失敗パターンを発見**
   - 短時間に連続切断が発生すると、GS2200Mがリソース枯渇状態に陥る
   - この状態では全ての新規接続がRSTで拒否される
   - Phase 9の再接続ロジックでは回復不可能

3. **GS2200Mの根本的制限**
   - TCP接続管理のリソースが限定的
   - 短時間の接続/切断サイクルに脆弱
   - 状態回復には再起動が必要

### 9.2 推奨アクション

1. **即座**: 再接続間隔にウェイトを追加（5秒）
2. **短期**: バックオフアルゴリズム実装
3. **中期**: GS2200M状態監視・診断機能追加
4. **長期**: ESP32-S3への移行検討
