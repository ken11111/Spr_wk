## エグゼクティブサマリー

pcapキャプチャにより、TCP切断の直接原因を特定した。

**結論: GS2200M (Spresense) が FIN パケットを送信して接続を能動的に閉じた**

切断トリガー: パケットロス → 重複ACK → 再送 → GS2200M内部エラー → FIN送信

## 2. 切断原因の分析

### 2.1 パケットロスの発生

```
┌────────────────────────────────────────────────────────────────┐
│ GS2200M WiFi Module                                            │
│                                                                │
│ 21:59:40.943 送信: seq 166755961-166755965 (4バイト) ✅       │
│                                                                │
│ 21:59:41.351 送信: seq 166757429-... (1460バイト)             │
│              ↑                                                 │
│              seq 166755965-166757429 の間が欠落 (1464バイト)  │
│                                                                │
│ 原因推定:                                                      │
│   - WiFi電波干渉でパケットロス                                 │
│   - GS2200M内部バッファ競合                                    │
│   - SPI転送エラー                                              │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 GS2200Mの異常動作

**通常のTCP動作:**
1. パケットロス検出
2. 再送タイマー待ち (RTO)
3. 再送実行
4. ACK受信で継続

**今回のGS2200M動作:**
1. パケットロス発生
2. PCから重複ACK x11受信
3. 1.5秒後に再送 ✅
4. **再送直後にFIN送信** ← 異常

### 2.3 FIN送信の原因仮説

```
┌────────────────────────────────────────────────────────────────┐
│ GS2200M内部状態の推定                                          │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│ 仮説1: 再送リトライ上限到達                                    │
│   - GS2200Mの再送カウントが上限に達した                        │
│   - usrsockが接続を「失敗」と判断                              │
│   - 自動的にFINを送信して終了                                  │
│   可能性: 60%                                                  │
│                                                                │
│ 仮説2: 内部バッファ枯渇                                        │
```

## 4. 重要な発見

### 4.1 確定事項

1. **GS2200Mが能動的にFINを送信した** (pcapで確認)
2. **パケットロスが発生していた** (シーケンス番号ギャップ)
3. **PCは正常に動作していた** (重複ACKは正しい応答)
4. **再送は成功した** (PCは累積ACKを返した)
5. **再送成功直後にFIN送信** (36ms後)

### 4.2 PC側は無関係

```
PC側の動作 (全て正常):
✅ パケットロス検出 → 重複ACK送信
✅ 再送パケット受信 → 累積ACK送信
✅ FIN受信 → ACK + FIN送信
✅ 接続終了処理完了
```

### 4.3 問題はGS2200M内部

```
GS2200Mの異常動作:
❓ 再送成功したのにFINを送信
❓ 接続を維持できなかった
❓ usrsockがエラー状態に遷移
```

## 5. 対策の優先度更新

### 5.1 短期対策 (効果: 高)

1. **自動再接続機能の実装**
   - FINを受信したら自動的に再接続
   - ユーザー体験への影響を最小化

2. **パケットロス耐性の向上**
   - TCP_NODELAYの再検討
   - TCP送信バッファサイズの調整

### 5.2 中期対策 (効果: 中)

1. **フレームレート制限**
   - カメラFPSを10-15fpsに制限
   - GS2200Mの負荷軽減
   - パケットロス発生確率を低下

2. **WiFi環境の改善**
   - 5GHz帯への移行 (対応ルーター必要)
   - アンテナ位置の最適化

### 5.3 長期対策 (効果: 根本解決)

1. **高性能WiFiモジュールへの移行**
   - ESP32 (より堅牢なTCPスタック)
   - 11n/ac対応モジュール

## 6. 結論

### 6.1 切断の直接原因

**GS2200M WiFiモジュールが、パケットロス発生後の再送処理において、
再送成功にもかかわらずFINパケットを送信して接続を終了した。**

### 6.2 根本原因の推定

GS2200Mのusrsock実装またはTCPスタックにおいて、
再送リトライカウントまたは内部エラー状態により接続が終了された。

### 6.3 責任の所在

| コンポーネント | 責任 | 備考 |
|---------------|------|------|
| PC (Rust GUI) | 0% | 全て正常動作 |
| WiFi環境 | 10% | パケットロスのトリガー |
| **GS2200M** | **90%** | 再送成功後のFIN送信は異常 |
