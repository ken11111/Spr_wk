ステートフル読み取りに変更することで、パケット境界情報を保持し、毎回のsync検索を不要化。初回接続時のみsync検索を行い、以降は正確なパケットサイズに基づいて読み取る。

#### 問題の本質（Phase 7.2cまで）

**ステートレスsync検索の問題:**
```rust
// Phase 7.2cまでの実装（問題あり）
pub fn read_packet(&mut self, buffer: &mut [u8]) -> io::Result<usize> {
    // 毎回パケット読み取りのたびにsync word検索
    loop {
        read 1 byte from TCP stream;
        if sync_word found { break; }
        // 最悪48KBスキップ → 前のパケット完全損失
    }

    // パケットサイズ情報を読み取り
    read packet header;
    read jpeg_size bytes;

    // 次回のread_packet()呼び出し時、またsync検索が必要
    // → TCP read()がパケット途中から開始すると、前のパケットをスキップ
}
```

**なぜ79%取りこぼしになるか:**
1. TCP read()は「利用可能なバイト」を返す（パケット境界とは無関係）
2. 毎回sync検索 → 前回パケットの終了位置を覚えていない
3. パケット途中から読み取り開始 → sync発見までスキップ → パケット損失
4. 676パケット送信中、3〜5パケット中1パケットしか受信できない
5. **実測: 142パケット受信（21%）、534パケット損失（79%）**

**証拠:**
- Spresense: TCP送信234ms平均、676パケット100%成功 → ネットワーク層は正常
- PC: Sync wordスキップ11-88KB → パケット1-2個分を毎回スキップ
- 実測79%損失 → 理論計算（3〜5パケット中1パケット = 20-33%成功率）と一致

#### Phase 7.3の解決策

**ステートフル読み取りロジック:**
```rust
// Phase 7.3の実装（修正版）
pub struct TcpConnection {
    stream: TcpStream,
    sync_established: bool,     // 初回sync完了フラグ
    internal_buffer: Vec<u8>,   // 内部バッファ（250KB）
    buffer_pos: usize,          // 内部バッファの現在位置
}

pub fn read_packet(&mut self, buffer: &mut [u8]) -> io::Result<usize> {
    // Step 1: 初回のみsync word検索
    if !self.sync_established {
        self.find_initial_sync()?;  // 1回だけ実行
        self.sync_established = true;
    }

    // Step 2: 内部バッファに十分なデータを確保（最低14バイト）
    self.ensure_buffer_has(14)?;

    // Step 3: sync wordを読み取り（すでに同期済み、検索不要）
    let sync_word = read_from_internal_buffer(4);

    // Step 4: パケットサイズを取得
    let packet_size = match sync_word {
        MJPEG_SYNC_WORD => {
            let jpeg_size = read_from_internal_buffer(8..12);
            14 + jpeg_size + 2  // ヘッダー + JPEG + CRC
        }
        // ... 他のパケットタイプ
    };

    // Step 5: パケット全体を内部バッファに確保
    self.ensure_buffer_has(packet_size)?;

    // Step 6: 出力バッファにコピー
    buffer[..packet_size] = internal_buffer[pos..pos+packet_size];

    // Step 7: バッファ位置を進める（次のパケットは正しい位置から開始）
    self.buffer_pos += packet_size;

    // 次回のread_packet()呼び出し時、sync検索は不要
    // → パケット境界情報を保持 → 取りこぼしなし
}
```

**キーアイデア:**
1. **初回のみsync検索**: 接続確立時の1回だけ
2. **内部バッファ管理**: TCP read()のタイミングを吸収
3. **パケット境界保持**: buffer_posでパケット終了位置を記憶
4. **正確なサイズ読み取り**: sync検索不要、ヘッダー情報から正確に読み取り

## 根本原因分析

### 主要ボトルネック: PC側sync word検索ロジックの欠陥

**重要な事実:**
1. **Spresense側**: 676パケットすべて正常送信（TCP write成功率100%）
2. **PC側**: 142パケットのみ受信（21%）、534パケット取りこぼし（79%）
3. **結論**: **ネットワーク層での損失はなし**。問題はPC側の受信処理ロジック。

**根本原因:**

現在の実装は、**毎回パケット境界を検索**するため、TCPバイトストリームの途中から読み取りを開始すると、前のパケットをスキップしてしまう：

```rust
// 現在の問題ある実装 (tcp_connection.rs)
pub fn read_packet() {
    // 毎回sync wordを1バイトずつ検索
    loop {
        read 1 byte;
        if sync_word found { break; }
        // 最悪48KBスキップ → 前のパケット完全損失
    }
}
```

**なぜ79%取りこぼしになるか:**
- TCP read()は「利用可能なバイト」を返す（パケット境界とは無関係）
- 毎回sync検索 → 前回パケットの終了位置を覚えていない
- パケット途中から読み取り開始 → sync発見までスキップ → パケット損失
- これが繰り返されると、3〜5パケット中1パケットしか受信できない（損失率67-80%）

**証拠:**
- Spresense: TCP送信234ms平均 → 再送なし → ネットワーク層は正常
- PC: Sync wordスキップ11-88KB → パケット1-2個分を毎回スキップ
- 実測79%損失 → 理論計算と一致

### 副次的要因: GS2200M TCP送信性能（ユーザー体験への影響）

**これはパケット取りこぼしの直接原因ではない**が、以下の問題を引き起こす：

#### 1. GS2200M内部TCPバッファサイズ

- **症状**: 48KBパケットが平均234ms、最大1.2秒要する
- **分析**: GS2200Mは小さな内部TCP送信バッファ（< 48KB）を持つ可能性
- **メカニズム**:
  ```
  1. Spresenseがwrite(tcp_socket, 48KB_data)を呼び出し
  2. GS2200Mが最初の~16KBを内部バッファに受け入れ
  3. GS2200M SPIインターフェースが「バッファフル」（EAGAIN）を返す
  4. Spresenseが10ms待機して再試行（最大3回）
  5. GS2200MがWiFi経由でバッファをゆっくり排出（11-72 Mbps理論値）
  6. 全48KB送信まで処理を繰り返し
  7. 総時間: WiFi状態に応じて200-1,200ms
  ```

#### 2. SPIインターフェースボトルネック

- **GS2200Mインターフェース**: SPI @ 最大10 MHz（NuttXドライバ）
- **理論SPIスループット**: 10 Mbps = 1.25 MB/s
- **実測**: 171 KB/s = **SPI理論値の13.6%**
- **考えられる問題**:
  - SPI DMAが効率的に使用されていない
  - 割り込みモードの代わりにポーリングモード
  - GS2200Mファームウェアオーバーヘッド

#### 3. WiFi環境

- **距離**: 不明（テストで測定せず）
- **干渉**: 不明（チャンネル未指定）
- **信号強度**: GS2200Mドライバでログ記録なし
- **推奨**: Spresenseをルーターの近くでテスト

### 副次的問題: Sync Word検索オーバーヘッド

**問題:**
- PCはTCP読み取り後、sync wordを1バイトずつ検索する必要がある
- 大きなスキップ（最大88KB）は1-2パケット完全損失を示す
- 100KB検索範囲でも2回のエラーが発生

**メカニズム:**
```
TCPストリーム（バイト単位の到着）:
┌─────────────────────────────────────────────────────────┐
│ [Packet N-1 tail] [Packet N] [Packet N+1] [Packet N+2] │
└─────────────────────────────────────────────────────────┘
                         ↑
                    PCがここから読み取り開始（Packet Nの途中）

検索プロセス:
1. 4バイト読み取り: XX XX XX XX（sync wordではない）
2. 1バイトスライド: XX XX XX XX（sync wordではない）
3. ~48,000回繰り返し（Packet N全体）
4. Packet N+1の先頭でsync wordを発見
5. 結果: Packet Nが完全に損失
```

**なぜこれが起こるか:**
- TCPはバイトストリームプロトコル（メッセージ境界なし）
- PCはパケット境界を手動で同期する必要がある
- PC接続がパケット途中で発生すると、同期が失われる
- TCPバッファ充填中にPCが読み取ると、同期が失われる

**期待よりも悪い理由:**
- USB Serial使用時: ハードウェアフレーミングが同期を提供
- TCP使用時: 純粋なバイトストリーム、フレーミングなし

pub struct TcpConnection {
    stream: TcpStream,

    internal_buffer: Vec<u8>,  // 内部バッファ（250KB）
    buffer_pos: usize,
}

pub fn read_packet(&mut self, buffer: &mut [u8]) -> io::Result<usize> {
    // 初回のみsync word検索
    if !self.sync_established {
        self.find_initial_sync()?;
        self.sync_established = true;
    }

    // 内部バッファに十分なデータを確保（最低14バイト）
    self.ensure_buffer_has(14)?;

    // sync wordを読み取り（すでに同期済み、検索不要）
    let sync_word = read_from_internal_buffer(4);

    // パケットサイズを取得
    let packet_size = match sync_word {
        MJPEG_SYNC_WORD => {
            let jpeg_size = read_from_internal_buffer(8..12);
            14 + jpeg_size + 2  // ヘッダー + JPEG + CRC
        }
        // ... 他のパケットタイプ
    };

    // パケット全体を確保してコピー
    self.ensure_buffer_has(packet_size)?;
    buffer[..packet_size] = internal_buffer[pos..pos+packet_size];

    // 次のパケットは必ず正しい位置から開始
    self.buffer_pos += packet_size;
    Ok(packet_size)
}

- 平均234ms TCP送信時間（期待値の10-23倍遅い）

- **注意**: これはパケット取りこぼしの直接原因ではない
