# ADR 006: Progressive Resolution Validation Strategy for Risk-Mitigated Development

**作成日**: 2026-02-10
**バージョン**: 1.0
**ステータス**: 受諾済み
**対象システム**: Spresenseセキュリティカメラ 全Phase
**技術影響度**: 中

## 1. 決定概要

### 背景
防犯カメラシステムの要求仕様として最終的にFull HD (1920×1080) @ 30fps H.264ストリーミングを目指していたが、Spresenseの処理能力・USB帯域・WiFi制約等の技術的制限が不明確であった。一度にFull HDで実装を開始した場合、複数の制約が同時に発現し、問題の切り分けが困難になるリスクがあった。

### 決定内容
**段階的解像度検証アプローチ**を採用し、QVGA → VGA → HD → Full HDの順で解像度を段階的に向上させ、各段階で技術的制約を特定・解決してから次段階に進む。

**実装戦略**:
- **Phase 1A**: QVGA (320×240) MJPEG @ 30fps（技術的基盤確立）
- **Phase 1.5**: VGA (640×480) MJPEG @ 30fps（中間検証）
- **Phase 1B**: HD (1280×720) H.264 @ 30fps（高解像度検証）
- **Phase 2**: Full HD (1920×1080) H.264 @ 30fps（最終目標達成）

### 影響範囲
- プロジェクト全体の開発戦略・工程計画
- 技術的リスクの早期発見・対応プロセス
- ハードウェア制約の段階的理解
- 品質保証・テスト戦略

## 2. 技術的根拠

### 課題分析
**複合的制約による技術リスク**:
```
Full HD直接実装時の予想される問題:
├─ USB帯域制約: Full HD H.264 5Mbps vs USB 12Mbps（帯域ギリギリ）
├─ CPU処理能力: Cortex-M4F×6 @ 156MHzでのH.264エンコード負荷
├─ メモリ制約: 1.5MB RAM vs Full HDフレームバッファサイズ
├─ WiFi安定性: GS2200Mでの大容量データ継続転送
└─ 統合問題: 複数制約の同時発現による問題特定困難
```

**リスク分析**:
- 問題発生時の原因切り分けが困難
- 開発期間の予測不可能性
- 技術的実現可能性の不確実性

### 代替案検討

| 選択肢 | メリット | デメリット | 採用理由 |
|-------|---------|-----------|----------|
| **段階的解像度検証** | ・リスク早期発見<br>・問題切り分け容易<br>・確実な進歩実感 | ・開発期間長期化<br>・中間目標の追加工数 | ✅ **採用**：確実性とリスク管理 |
| Full HD直接実装 | ・最短開発期間<br>・最終目標直接達成 | ・高リスク<br>・問題特定困難<br>・失敗時の影響大 | ❌ リスク過大 |
| 並行開発（複数解像度同時） | ・開発期間短縮可能<br>・比較検証容易 | ・リソース分散<br>・複雑性増大<br>・品質管理困難 | ❌ リソース制約 |
| 既存ライブラリ活用 | ・実装工数削減 | ・Spresense固有最適化不可<br>・制約理解が不十分 | ❌ 学習目的に不適 |

### 選択理由
1. **確実な技術基盤構築**: 各段階で技術的課題を確実に解決
2. **リスク分散**: 複数制約を段階的に発見・対応
3. **知見蓄積**: 段階的学習による深い理解獲得
4. **プロジェクト成功率向上**: 早期の技術的検証による失敗リスク軽減

## 3. 実装詳細

### 技術仕様
**Phase別検証マトリックス**:

| Phase | 解像度 | フォーマット | FPS目標 | 主要検証項目 | 制約発見 |
|-------|--------|-------------|---------|-------------|----------|
| **1A** | QVGA (320×240) | MJPEG | 30fps | USB CDC, プロトコル基盤 | TTY Raw Mode要件 |
| **1.5** | VGA (640×480) | MJPEG | 30fps | V4L2最適化, CRC性能 | 3バッファ制限, 77%CRC改善 |
| **1B** | HD (1280×720) | H.264 | 30fps | H.264エンコード, USB帯域 | USB 12Mbps制約検証 |
| **2A** | Full HD (1920×1080) | H.264 | 30fps | WiFi転送, 総合性能 | GS2200M TCP制約 |

**検証成功基準（各Phase）**:
```
Phase 1A (QVGA):
✅ 90/90フレーム成功率（100%）
✅ プロトコル安定性確認
✅ USB CDC基盤技術確立

Phase 1.5 (VGA):
✅ 11fps安定動作（目標30fpsの37%）
✅ V4L2制約発見・対応
✅ CRC最適化実装（77%改善）

Phase 1B (HD):
⏳ H.264エンコード検証
⏳ USB帯域限界確認
⏳ 品質・性能バランス調整

Phase 2A (Full HD):
⏳ WiFi転送安定性
⏳ 総合システム性能
⏳ 最終要求仕様達成
```

### 段階移行判定基準
**Next Phase移行条件**:
1. **技術的安定性**: 連続動作30分以上エラーなし
2. **性能目標達成**: FPS 70%以上達成または制約明確化
3. **制約特定完了**: 発見された制約への対策確立
4. **再現可能性**: 同一環境での結果再現性確保

**制約発見時の対応方針**:
```
制約発見 → 原因分析 → 対策検討 → 実装・検証 → 次Phase判断

例：Phase 1.5でのV4L2 3バッファ制限
発見: 5バッファ要求でエラー
分析: ドライバハードウェア制限
対策: actual_buffer_count使用
検証: 90フレーム100%成功
判定: Phase 1B移行可能（制約は文書化）
```

### 🔴 GATE-1 (P1.5 → P1B 移行判定) の判断材料

`02_specifications/architecture/SPRESENSE_TCP_CONSTRAINTS.md` (2026-04-27 作成)
で抽出した Spresense + GS2200M の構造的天井に基づき、本ゲートで以下を判定する:

#### 判定 A: ソフト最適化のみで Phase 1B/2A 達成可能か?

**HD (1280×720) H.264 30fps の帯域要件**:
- H.264 約 2-5 Mbps = **250-625 KB/s**
- I-frame は 50-200 KB/frame の可能性

**GS2200M 帯域天井 (制約マップより)**:
- SPI 4 MHz 理論 500 KB/s, **実効 200-300 KB/s**
- → HD H.264 の帯域要件は天井を **大幅超過**
- → Spresense 単体で Phase 1B 達成は **物理的に困難**

**Full HD (1920×1080) H.264 30fps**:
- 約 5 Mbps = **625 KB/s** (実効 200-300 KB/s に対し **2-3 倍超過**)
- I-frame は 200 KB+ → MJPEG_BATCH_SIZE=1 でも `MAX_BATCH_PACKET = 122 KB` を超過、新たな分割戦略が必須

#### 判定 B: ハードウェア変更で何が必要か?

| 候補 | 帯域改善 | 移植コスト | 既存資産損失 |
|---|---|---|---|
| **SPI 周波数引き上げ** (`WL_GS2200M_SPI_FREQUENCY` 増加) | 2-4× の可能性 | 小 | なし |
| **USB 経由切替** (ADR-001 系統) | USB 12 Mbps = 1.5 MB/s | 中 (TCP→USB プロトコル変更) | TCP 系統廃止 |
| **ESP32-S3 移行** | 内蔵 WiFi、Cortex-M4F、SPI 制約解消 | 大 (ADR-006 HW-1〜HW-4) | NuttX/SDK 一部破棄 |
| **Raspberry Pi CM4/CM5** | Linux + H.264 HW エンコード | 最大 | Spresense 資産ほぼ放棄 |

#### 判定 C: 各 ADR への波及

ハード変更時、以下 ADR の有効性を再評価必要:
- **ADR-001 (TTY Raw Mode)**: USB 経由切替なら有効、ハード変更なら別系統
- **ADR-002 (TCP Health Monitoring)**: GS2200M 廃止なら本 ADR は不要 (新ハードでは別の監視戦略が必要)
- **ADR-003 (V4L2 RING Buffer)**: ISX012/019 を使い続けるなら有効、新ハードで Linux V4L2 系に統一可能
- **ADR-005 (3-Thread Pipeline)** および **ADR-008 (Channel Bounded)**: PC 側設計なので影響小、ただし帯域改善で容量再検討 (ADR-008 §5)
- **ADR-004 (CRC Lookup)**: プロトコル変更時は再評価

#### GATE-1 判定の出力

| 判定 | 進路 |
|---|---|
| ✅ Spresense 継続可能 (理想) | HW-1〜HW-4 をスキップ、P1B 直行 (現状の制約マップから可能性低) |
| ⚠️ SPI 周波数引き上げで P1B のみ達成 | HW-1 評価、HW-2〜HW-4 は条件次第 |
| ❌ HW 移行必須 | HW-1〜HW-4 + GATE-2 を経由 (+15 週) |

→ GATE-1 の出力により、後続 Phase の見積もり精度を確保する。

## 4. 検証結果

### 実装成果
**Phase 1A（QVGA MJPEG）完了実績**:
- **成功率**: 90/90フレーム（100%）
- **主要発見**: TTY Raw Mode必須（データ破損防止）
- **基盤確立**: USB CDC-ACM, MJPEGプロトコル
- **移行判定**: ✅ Phase 1.5へ移行承認

**Phase 1.5（VGA MJPEG）完了実績**:
- **性能達成**: 11fps（目標30fpsの37%、実用レベル）
- **主要発見**: V4L2ドライバ3バッファ制限、CRC最適化77%改善
- **制約対応**: バッファ管理最適化、性能ボトルネック特定
- **移行判定**: ⚠️ Phase 1Bは慎重に進行（HD要検証）

### 段階的検証効果の定量化
**リスク軽減効果**:
| リスクカテゴリ | 段階的検証なし | 段階的検証あり | 軽減効果 |
|---------------|---------------|---------------|----------|
| 技術的実現可能性 | 不明（Full HD時点） | Phase毎に確認済み | **早期確定** |
| 問題特定時間 | 数週間（複合問題） | 1-3日（単一問題） | **80%短縮** |
| 開発成功率 | 推定60%（高リスク） | 推定90%（段階的） | **+50%向上** |
| 技術知見蓄積 | 表面的 | 体系的・深い理解 | **質的向上** |

**技術的知見蓄積例**:
- USB CDC制約とその回避策（TTY Raw Mode）
- V4L2ドライバの実装制限とハードウェア依存性
- CRC計算のボトルネック特性と最適化手法
- 組み込みシステムでの性能測定・分析手法

## 5. 運用考慮事項

### 段階移行の判断プロセス
**Phase移行評価会議**:
1. **技術的達成度評価**（性能・安定性・制約対応）
2. **次Phaseリスク分析**（予想される課題・対策案）
3. **リソース・工程検討**（必要工数・期間見積もり）
4. **Go/No-Go判断**（移行承認・延期・戦略変更）

**文書化要求事項**:
- Phase完了レポート（成果・制約・次Phase推奨事項）
- 制約発見記録（原因・影響・対策・回避方法）
- 性能ベンチマーク結果（定量データ・比較分析）
- 技術的教訓まとめ（今後のプロジェクトへの適用指針）

### 注意点
- **中間目標の追加工数**: Phase毎の完成度向上によりオーバーヘッド発生
- **最終目標への影響**: 中間制約により最終仕様変更の可能性
- **技術的負債**: 段階的実装により一時的な技術的妥協が必要
- **スケジュール管理**: 各Phase期間の見積もり精度が重要

### 成功要因
- **明確な移行基準**: 客観的な判断基準の事前設定
- **制約の受容**: 発見された制約を設計制約として受け入れる柔軟性
- **知見の文書化**: 各Phaseで得られた技術的知見の確実な記録
- **継続的改善**: 後続Phaseで前Phaseの課題を改善する仕組み
