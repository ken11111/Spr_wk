## 1. システム概要

### 1.1 システムの目的

Spresense HDRカメラボードを使用した防犯カメラシステムを構築する。

**主要機能**:
- ✅ リアルタイム映像配信（Spresense → PC）
- ✅ 映像録画とPC側への保存
- ✅ Rust実装によるPC側ソフトウェア

> 具体的なユースケース (起動 / ストリーミング / 動き検出録画 / 切断復旧 / 障害時介入) は [`../02_specifications/use_cases/`](../02_specifications/use_cases/) を参照。

### 1.2 システム構成（暫定）

```
┌─────────────────────┐         ┌─────────────────────┐
│  Spresense          │         │  PC (Rust)          │
│  + HDR Camera       │ ◄─────► │  + 映像受信         │
│                     │  WiFi/  │  + 録画保存         │
│  - 映像取得         │  USB    │  - ストレージ管理   │
│  - 圧縮・送信       │         │  - 表示（Optional）│
└─────────────────────┘         └─────────────────────┘
```

## 2. 機能要求

### 2.1 映像取得（Spresense側）

**確定事項**:
- ✅ HDRカメラボード使用 (ISX012)

#### Q1: 映像解像度・フレームレート

以下のどれを優先しますか？

| オプション | 解像度 | FPS | 用途 |
|-----------|--------|-----|------|
| A. 高画質 | 1920x1080 (Full HD) | 15-30 fps | 詳細な記録重視 |
| B. 標準画質 | 1280x720 (HD) | 30 fps | バランス型 |
| C. 低画質・高速 | 640x480 (VGA) | 60 fps | 動き検出重視 |
| D. カスタム | **要指定** | **要指定** | - |

**質問**:
- 希望する解像度は？
- 希望するフレームレートは？
- 画質と通信帯域のバランスは？

**回答 (v0.1 暫定)**: A (Full HD)

📌 **実装事実 (Phase 1.5 時点)**:
- 実装は **VGA 640×480 / 30 fps** で確定 (`apps/examples/security_camera/config.h`)
- Phase 1.5 で VGA 最適化済 (37.33 fps を一時記録)
- 暫定回答 A (Full HD 1920×1080) は **構造的天井 #1 (GS2200M `tx_buff[1]`) で達成不可**
- Full HD 移行は Tier 2/3 ハード移行が前提 (QAS-6 / ADR-006 GATE-1 参照)
- → **v1.0 確定値: 640×480 @ 30 fps (現ハード上限)**

#### Q2: HDR機能の使用

**質問**:
- HDR機能を有効にしますか？
  - [x] はい（明暗差の大きい環境向け）
  - [ ] いいえ（通常のカメラとして使用）
- HDRによる処理遅延は許容できますか？
  - いいえ、最大限遅延は抑えてください

📌 **実装事実 (現状)**:
- `CONFIG_CAMERA_HDR_ENABLE = false` (`config.h`) — 実装で**無効化**
- HDR を有効にすると遅延増大の可能性あり、現状は無効化が妥当
- → **v1.0 確定値: HDR 無効** (要求 vs 実装の乖離: ユーザー要求は HDR 有効だが実装は無効)

#### Q3: 映像圧縮方式

以下のどの方式を使用しますか？

| 方式 | メリット | デメリット | Spresense対応 |
|------|---------|-----------|--------------|
| JPEG | 実装簡単、対応広い | 連続フレームで効率悪い | ✅ 標準対応 |
| H.264 | 高圧縮率、標準的 | エンコード負荷高い | ✅ ハードウェア対応 |
| H.265/HEVC | 超高圧縮率 | 処理負荷非常に高い | ❌ 非対応 |
| RAW転送 | 無圧縮、品質 | 帯域幅大 | ✅ 可能 |

**質問**:
- 圧縮方式の希望は？
- ビットレート/品質の目標は？
- リアルタイム性と録画品質のどちらを優先？

**回答 (v0.1 暫定)**: H.264

📌 **実装事実 (Phase 8+)**:
- 実装は **MJPEG (連続 JPEG)** で確定
- ISX012 は JPEG 直接出力 (`V4L2_PIX_FMT_JPEG`)
- `encoder_manager.c` (H.264 path) は Makefile で compile されるが**呼び出し 0 件 = dead code**
- PC 側 `mp4_recorder.rs` で受信後 ffmpeg `libx264` で MP4 化 (録画ファイルのみ H.264)
- → **v1.0 確定値: 転送=MJPEG, 録画ファイル=MP4 (H.264)**

### 2.2 通信方式

#### Q4: 通信インターフェース

以下のどれを使用しますか？

| 方式 | 帯域幅 | メリット | デメリット |
|------|--------|---------|-----------|
| **USB CDC** | ~12 Mbps | 安定、簡単 | ケーブル必要 |
| **WiFi (TCP/IP)** | ~数十Mbps | 無線、柔軟 | 設定複雑、遅延 |
| **Ethernet (拡張)** | ~100 Mbps | 高速、安定 | 拡張ボード必要 |

**質問**:
- Spresense設置場所は？（PCとの距離）
- 有線/無線どちらを希望？
- WiFiを使う場合、アクセスポイントは用意済み？


**回答 (v0.1 暫定)**: 最終的にはWiFi、テストのために最初はUSB接続から始める

📌 **実装事実 (Phase 7+)**:
- USB CDC-ACM **両対応** (`/dev/ttyACM0`)、Phase 1-6 で USB 開発、Phase 7+ で WiFi 主路
- WiFi: GS2200M モジュール (SPI 4 MHz 経由), TCP port 8888
- WiFi 路は構造的天井 #1〜#5 で性能限界
- USB 路は安定だが Tier C (USB-only) を保険として保持
- → **v1.0 確定値: 両対応 (WiFi 主路, USB 副路)**

#### Q5: 通信プロトコル

以下のどれを使用しますか？

| プロトコル | 用途 | メリット |
|-----------|------|---------|
| **カスタムバイナリ** | 専用システム | 最小オーバーヘッド |
| **RTSP** | 標準ストリーミング | 既存ツール利用可 |
| **WebSocket** | Web統合 | ブラウザ対応 |
| **gRPC** | 高性能RPC | 型安全、効率的 |

**質問**:
- 既存の標準プロトコルを使う？
- それともシンプルなカスタムプロトコル？
- 将来的にWebブラウザからアクセスする可能性は？

**回答 (v0.1 暫定)**: RTSP

📌 **実装事実 (Phase 1+)**:
- 実装は **カスタム MJPEG プロトコル** (RTSP ではない)
- ヘッダ: sync_word (4B) + sequence (4B) + size (4B), 末尾に CRC-16-CCITT (2B)
- sync_word: `0xCAFEBABE` (単発), `0xCAFEBABF` (batch), `0xCAFEBEEF` (metrics)
- 暫定回答 RTSP は **未実装、採用予定なし** (Spresense 上での RTSP スタック実装コスト大)
- → **v1.0 確定値: カスタム MJPEG プロトコル (TCP/8888)**

詳細: [`../02_specifications/interface/protocol/MJPEG_PROTOCOL_SPEC.md`](../02_specifications/interface/protocol/MJPEG_PROTOCOL_SPEC.md)

## 3. 非機能要求

### 3.1 パフォーマンス要求

#### Q16: 許容遅延

映像の遅延はどの程度許容できますか？

| 遅延 | 用途 |
|------|------|
| <100ms | リアルタイム監視 |
| <1s | 一般的な監視 |
| <5s | 録画メイン |

**質問**: 許容遅延は？

**回答 (v0.1)**: 1sがMust、100msはWant

📌 **実装事実 (Phase 8/9 実測)**:
- **1s Must**: ✅ **達成** (Phase 8 平均 134 ms / Phase 9 平均 227 ms)
- **100ms Want**: 🔴 **未達** (構造的天井 #1 `tx_buff[1] × 1500B` で**物理的に達成不可**)
- 詳細: QAS-2 (`../02_specifications/quality/QUALITY_ATTRIBUTE_SCENARIOS.md`)
- → **v1.0 確定値**:
  - Must: 平均遅延 < 1s (✅ 達成)
  - Want: 平均遅延 < 100ms — **構造的天井により未達、Tier 2/3 移行後に再評価**

#### Q17: 録画の信頼性

フレームドロップは許容できますか？

**質問**:
- [ ] 完全録画必須（フレームドロップNG）
- [x] 多少のドロップは許容（ネットワーク状況次第）

📌 **実装事実 (Phase 8/9 実測)**:
- 実測ドロップ率: Phase 8: **53.7%** → Phase 9: **74.2-75.5%** (悪化)
- 「多少」の閾値が要求書で未定義のため評価困難
- 動画として実用限界に近い品質
- → **v1.0 確定値**:
  - 許容ドロップ率: ≤ 30% を目標 (但し現状未達, ハード制約)
  - 現状: 50-75% で実質「動画」として劣化、要再検討

  - 設計目標: 復旧時間 30s → 2.8s (90% 削減)
  - 実測: PC FPS 6.74 → 2.77 (-59% 悪化), ドロップ率 53.7% → 74.2% (悪化)
  - 4 回目以降は RST 拒否で失敗、5 回失敗後 FAILED 状態固着
- 根本原因: GS2200M 構造的天井 #1 (`tx_buff[1]` 完全直列化) → 再接続では解消不可
- → **v1.0 確定値**:
  - 自動再接続を試行 (max=5)、ただし**根本解決にはハードウェア移行 (Tier 2/3/C) が必要**
  - 5 回失敗後の人手介入手順の文書化が必要 (運用ランブック, 別タスク)

詳細: [`../03_achievements/architecture_decisions/system_architecture/ADR_002_NETWORKING_TCP_HEALTH_MONITORING.md`](../03_achievements/architecture_decisions/system_architecture/ADR_002_NETWORKING_TCP_HEALTH_MONITORING.md) v1.1

### 3.3 ハードウェア制約による達成限界 (新規 v1.0)

> **本セクションは v1.0 で追加**: Phase 9 で判明した GS2200M 構造的天井がパフォーマンス・信頼性 NFR の達成可否を支配する事実を要求書側に反映する。

#### 3.3.1 構造的天井 (改変不能な物理上限)

| # | 制約 | 影響する NFR |
|---|---|---|
| #1 | GS2200M `tx_buff[1] × 1500B` (送信完全直列化) | Q16 100ms Want, Q17 ドロップ率, Q19 再接続 |
| #2 | NuttX IOB プール 8×196B=1568B (流量制御無し) | Q16 遅延, Q19 再接続 |
| #3 | usrsock PREALLOC_CONNS=6 | 多接続シナリオ (本プロジェクト軽微) |
| #4 | Spresense RAM 1.5 MB | Q1 Full HD, Q3 H.264, Q24 セキュリティ (TLS 不可) |
| #5 | GS2200M 内部 (非公開・改変不能) | チューニング不可 |

詳細: [`../02_specifications/architecture/SPRESENSE_TCP_CONSTRAINTS.md`](../02_specifications/architecture/SPRESENSE_TCP_CONSTRAINTS.md), [`../02_specifications/quality/GLOSSARY.md`](../02_specifications/quality/GLOSSARY.md) §2

#### 3.3.2 達成不可な NFR と Tier 移行の必要性

| NFR | 現状 (Tier 1) | 必要 Tier | 移植コスト |
|---|---|---|---|
| Full HD 30 fps (Q1 暫定 A) | 🔴 不可 | Tier 2 (ESP32-S3) または Tier 3 (RPi CM5) | +14 週 / 最大 |
| 100ms 遅延 (Q16 Want) | 🔴 不可 | Tier 2/3 | 同上 |
| 再接続 2.8s 復旧 (ADR-002 v1.0 目標) | 🔴 逆効果 | Tier 2/3/C | 同上 |
| TLS/暗号化 (Q24 設計) | 🔴 RAM 不足 | Tier 2/3 | 同上 |

→ **Phase 12 以降の中核タスク**: Tier 移行判断 (詳細: QAS-6, ADR-006 GATE-1)

## 6. システム制約

### 6.1 技術的制約

**Spresense制約**:
- CPU: CXD5602 (ARM Cortex-M4F × 6コア)
- メモリ: **1.5MB RAM** (構造的天井 #4)
- ストレージ: 8MB Flash
- カメラ: 最大5MP、JPEG/YUVサポート

**通信制約**:
- USB: 最大12Mbps (Full Speed)
- WiFi: 802.11 b/g/n (理論値最大150Mbps)
- **GS2200M 経由実効帯域**: SPI 4 MHz 経由で 200-300 KB/s (構造的天井 #1)

### 6.2 ソフトウェア制約

**Spresense側**:
- OS: NuttX RTOS
- 言語: C/C++
- SDK: Spresense SDK
- TCP スタック: **NET_TCP_NO_STACK=y** (NuttX bypass, GS2200M 委譲)

**PC側**:
- 言語: Rust（確定）
- 最小サポートRustバージョン: 2021 edition (`Cargo.toml`)

#### Q23: Rustクレート選定

使用するRustクレートの希望は？

**候補**:
- 映像処理: `ffmpeg`, `gstreamer`, `opencv-rust`
- 通信: `tokio`, `async-std`, `serialport-rs`
- GUI: `egui`, `iced`, `gtk-rs`, `druid`

**質問**: 特定のクレートを使いたい？

**回答 (v0.1)**: Rustの知識がなく回答不可、別途解説要望

📌 **実装事実 (現状, `Cargo.toml`)**:
- GUI: **eframe (egui)** — シンプル、即時モード
- シリアル: **serialport-rs**
- 録画: **ffmpeg-cli** (subprocess 起動)
- 動き検出: **ndarray** + 自前ロジック
- 並行: **std::sync::mpsc** (3-thread Pipeline, ADR-008 で bounded(3) 採用)
- → **v1.0 確定値: 上記クレートで確定 (互換性ある変更は許容)**
