# Phase 7 バッファ・キュー設計分析とパフォーマンス評価

**Date**: 2026-01-13
**Target**: WiFi/TCP Transport (Phase 7.2c, 7.3, 7.3.1, 7.3.2)
**Purpose**: シーケンス図とバッファ・キュー図による動作解析

## エグゼクティブサマリー

Phase 7の各バージョンの動作を、シーケンス図とバッファ・キュー図で可視化し、性能差の根本原因を解明します。

**主要な発見:**
1. **Phase 7.3.1の偶然の性能向上**: 2バイトずれによるsync再検索が、150KB待ち行列再構築を誘発し、FPSが向上
2. **Phase 7.3.2の正確な実装**: パケット境界が正確で、全てのフレームを正しく処理
3. **GS2200M WiFi hardware制約**: TCP送信時間160-300ms/packetがボトルネック

| Phase | パケット処理 | FPS | エラー検出 | 評価 |
|-------|------------|-----|----------|------|
| **7.2c** | ステートレス（毎回sync検索） | 0.76 fps | 79%エラー | ❌ 失敗 |
| **7.3** | ステートフル（初回のみsync検索） | 1.52 fps | 0%エラー | ✅ 成功 |
| **7.3.1** | 2バイトずれ（偶然の性能向上） | 3.3 fps | エラー隠蔽 | ⚠️ バグによる副作用 |
| **7.3.2** | 正確なパケット境界 | 理論値 | 全て検出 | ✅ **正しい実装** |

## 1. Phase 7.2c: ステートレス方式の問題点

### 1.1 シーケンス図（Phase 7.2c）

```
Spresense (GS2200M WiFi)     TCP Stream               PC (tcp_connection.rs)
        |                         |                           |
        |--- Packet #1 (57KB) --->|                           |
        |    [CA FE BA BE]         |                           |
        |    [14-byte header]      |                           |
        |    [JPEG 57KB]           |                           |
        |    [CRC 2 bytes]         |                           |
        |                         |--- TCP read() ----------->|
        |                         |    (3 bytes returned)      | [CA FE BA] ← sync word途中
        |                         |<-------------------------- |
        |                         |--- TCP read() ----------->|
        |                         |    (remaining bytes)       | [BE][header][JPEG...]
        |                         |                           |
        |                         |                           | ❌ Sync word検出失敗
        |                         |                           | → 1バイトスライド検索開始
        |                         |                           | → 最大100KB検索
        |                         |                           | → 次のパケットのsync検出
        |                         |                           | → しかし既にパケット途中
        |                         |                           | → JPEG decodeエラー (79%)
```

### 1.2 バッファ状態図（Phase 7.2c）

```
TCP Stream (byte stream - メッセージ境界なし):
┌────────────────────────────────────────────────────────────────┐
│ [CA FE BA BE][Header 14][JPEG 57KB][CRC 2][CA FE BA BE]...    │
└────────────────────────────────────────────────────────────────┘
  ↓ TCP read() #1 (3バイト)
  [CA FE BA]

  ↓ Sync検索
  ❌ 0xBAFECA (不正) → スライド検索

  ↓ TCP read() #2 (57KB)
  [BE][Header 14][JPEG 57KB][CRC 2][CA FE BA BE]...

  ↓ 検索継続
  ✅ 0xCAFEBABE 発見 (次のパケット)

  ↓ しかし...
  ❌ 既にパケット途中から読んでいる
  ❌ JPEG decodeエラー
```

**問題点:**
- 毎パケット読み取り時にsync検索
- TCP read()のタイミングに依存
- Sync wordが2つのread()に分割される可能性
- パケット境界を保証できない

### 2.1 シーケンス図（Phase 7.3）

```
Spresense (GS2200M WiFi)     TCP Stream               PC (tcp_connection.rs)
        |                         |                           |
        | === 接続時（初回のみ） ==                           |
        |                         |                           | find_initial_sync()
        |                         |<--- TCP read() -----------|
        |                         |--- [CA FE BA BE] ------->| ✅ Sync発見
        |                         |                           |
        |                         |<--- TCP read(150KB) ------|
        |--- Packet #1,2,3... --->|--- [150KB data] -------->| ✅ 待ち行列構築
        |                         |                           | internal_buffer: 150KB
        |                         |                           | sync_established = true
        |                         |                           |
        | === 以降のパケット読み取り ==                        |
        |                         |                           | read_packet()
        |                         |                           | ✅ sync検索スキップ
        |                         |                           | ✅ buffer_posから読む
        |                         |                           | ✅ パケットサイズ情報使用
        |                         |                           | (14 + jpeg_size + 2)
        |                         |                           |
        |                         |                           | buffer_pos += packet_size
        |                         |                           |
        |                         |                           | ensure_buffer_has()
        |                         |<--- TCP read() (必要時)----|
        |--- Additional data ---->|--- [64KB data] --------->| ✅ バッファ補充
```

### 2.2 バッファ状態図（Phase 7.3）

```
初回sync検索後の内部バッファ:
┌───────────────────────────────────────────────────────────────────┐
│ internal_buffer (150KB capacity)                                  │
│ ┌─────────────────────────────────────────────────────────────┐   │
│ │[CA FE BA BE][Header][JPEG 57KB][CRC][CA FE BA BE][Header]...│   │
│ └─────────────────────────────────────────────────────────────┘   │
│  ↑                                   ↑                             │
│  buffer_pos = 0                      buffer_pos = 57303            │
└───────────────────────────────────────────────────────────────────┘

Packet #1 読み取り:
  sync_word = internal_buffer[0..4] = 0xCAFEBABE ✅
  jpeg_size = internal_buffer[8..12] = 57289
  packet_size = 14 + 57289 + 2 = 57303
  output_buffer[0..57303] = internal_buffer[0..57303]

✅ パケット境界が完全に保持される

**改善点:**
- 初回のみsync検索（1回のみ）
- 150KB待ち行列で2-3パケット分をバッファリング
- パケットサイズ情報でパケット境界を保証
- TCP read()のタイミング不確実性を吸収

        |                         |                           | (実際は57305必要)
        |                         |                           |
        |--- Packet #2 (58KB) --->|                           |
        |    [CA FE BA BE]         |                           | read_packet()
        |    [Header 14]           |                           | sync_word = buffer[57303..57307]
        |    [JPEG 58123]          |                           |   = [CRC 2][CA FE]
        |    [CRC 2]               |                           |   = 0x????CAFE ❌ 不明なsync
        |                         |                           |
        |                         |                           | sync_established = false
        |                         |                           | find_initial_sync()
        |                         |                           | ↓
        |                         |<--- TCP read(150KB) ------|
        |--- Packet #2,3,4... --->|--- [150KB data] -------->| ✅ 待ち行列再構築
        |                         |                           |
        |    (160-300ms)           |    (200ms for 150KB)     | ✅ 副作用: バッファリング
```

### 3.2 バッファ状態図（Phase 7.3.1）

```
Packet #1 読み取り後の内部バッファ:
┌───────────────────────────────────────────────────────────────────┐
│ internal_buffer                                                   │
│ ┌─────────────────────────────────────────────────────────────┐   │
│ │[CA FE BA BE][Header][JPEG 57KB][CRC][CA FE BA BE][Header]...│   │
│ └─────────────────────────────────────────────────────────────┘   │
│  ↑                                   ↑                             │
│  buffer_pos = 0                      buffer_pos = 57303 (誤)       │
│                                      (正しくは 57305)              │
│                                      ↓                             │
│                                      [CRC 2バイト] ← 残骸         │
└───────────────────────────────────────────────────────────────────┘

Packet #2 読み取り試行:
  sync_word = internal_buffer[57303..57307]
            = [CRC 2][CA FE]
            = 0x02D1CAFE (例) ❌ 不明なsync word

  ↓ エラー処理
  sync_established = false
  find_initial_sync() 呼び出し

  ↓ sync検索
  [CRC 2][CA FE BA BE] を検索
       ↑
       ここでsync発見

  ↓ 150KB待ち行列再構築
  TCP read(150KB) → Packet #2, #3, #4まとめて読む

  ↓ 結果
  ✅ 2バイトスキップされたが、再同期成功
  ✅ 副作用: 複数パケットを一度に読むため、FPS向上
```

### 3.3 なぜFPSが向上したのか

**Phase 7.3.2（正確）:**
```
Frame 1: TCP read (57KB) → 160ms
Frame 2: TCP read (58KB) → 180ms
Frame 3: TCP read (59KB) → 200ms
Frame 4: TCP read (60KB) → 220ms
--------------------------------------
合計: 760ms / 4 frames = 190ms/frame = 5.3 fps
```

**Phase 7.3.1（2バイトずれ）:**
```
Frame 1: TCP read (57KB) → 160ms
         ↓ sync_established = false
Frame 2-4: TCP read (150KB) → 200ms (まとめて読む)
--------------------------------------
合計: 360ms / 4 frames = 90ms/frame = 11.1 fps
```

**メカニズム:**
1. 2バイトずれ → sync再検索が毎パケット発生
2. 150KB再読み込み → 2-3パケット分を一度に読む
3. GS2200M WiFi送信時間（160-300ms/packet）を複数パケットで吸収
4. **結果: バグによる偶然の性能向上**

## 7. ボトルネック分析

### 7.1 GS2200M WiFi hardware制約

```
┌──────────────────────────────────────────────────────────────┐
│ GS2200M WiFi Module - TCP送信性能                             │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│ 測定値 (Phase 7.3テスト):                                     │
│ - 平均送信時間: 160-180 ms/packet (50-60KB JPEG)             │
│ - 最大送信時間: 472 ms/packet (ワーストケース)                │
│                                                               │
│ 理論最大FPS:                                                  │
│ - 1000ms / 160ms = 6.25 fps (最良ケース)                     │
│ - 1000ms / 300ms = 3.33 fps (複雑シーン)                     │
│                                                               │
│ 実測FPS:                                                      │
│ - Phase 7.3: 1.52 fps (理論値の24%)                          │
│ - Phase 7.3.1: 3.3 fps (理論値の52%, バグによる副作用)        │
│ - Phase 7.3.2: 理論値に近い (個別パケット読み取り)            │
│                                                               │
│ ボトルネックの原因:                                            │
│ 1. GS2200M WiFi hardware制約 (SPI通信速度)                   │

```

### 8.2 Phase 7.3.2 採用の理由

**技術的正確性:**
- ✅ パケット境界が完全に保証される
- ✅ CRC 2バイトを正しく処理
- ✅ sync wordが正確に検出される

**エラー検出:**
- ✅ JPEG validation errorが全て検出される
- ✅ ISX012 hardware limitationが正しく観測される
- ✅ デバッグが容易

**長期的安定性:**
- ✅ バグによる動作ではない
- ✅ TCP仕様に準拠
- ✅ 本番運用可能

### 8.3 今後の改善提案

**1. エラー回復モードの実装（ユーザー提案）**
```
無線通信である以上、データロスの考慮は必要。
データロスがあった時に止めるのではなく無視する方式に切り替える。
解析の際には検出・停止する方が都合が良いのでスイッチで切替可能にする。
```

**実装方針:**
- デフォルト: エラー回復モード（本番運用向け）
  - JPEG validation errorを無視して続行
  - フレームスキップ（前フレーム表示継続）
  - エラーカウントはログに記録
- `--strict`モード: エラーで停止（デバッグ・解析向け）
  - 現在の動作を維持
  - エラー発生時に停止

**2. GS2200M WiFi性能の最適化（オプション）**
- TCP送信バッファサイズの調整
- TCP_NODELAYの効果測定
- WiFi routerの変更（より高速なAP）

**3. ISX012 JPEG品質の調整（オプション）**
- JPEG圧縮率を下げる（画質 vs 性能のトレードオフ）
- シーンの複雑度に応じた動的調整

## 9. Phase 7の技術的貢献

### 9.1 解決した問題

1. **TCP byte streamプロトコルの課題**
   - メッセージ境界なし → ステートフル読み取りで解決
   - read()タイミング不確実性 → 150KB待ち行列で解決

2. **WiFi/TCPパケットロス**
   - 79%パケットロス → 0%に改善
   - sync再検索メカニズム → 自動回復

3. **GS2200M WiFi hardware制約の理解**
   - TCP送信時間測定: 160-300ms/packet
   - 理論最大FPS算出: 3.3-6.25 fps
   - ボトルネック特定

### 9.2 確立した技術

1. **ステートフル読み取りパターン**
   - 初回sync検索 + 150KB待ち行列
   - パケットサイズ情報による境界保証
   - TCP read()タイミング独立

2. **2段構えのキュー構造**
   - Spresense側: action_queue (Producer-Consumer)
   - PC側: internal_buffer (150KB待ち行列)
   - 両側でバッファリング → 安定性向上

3. **エラー検出と回復**
   - JPEG validation (Phase 4.1.1)
   - sync再検索による自動回復
   - エラー回復モード（実装予定）

## 付録A: 用語集

| 用語 | 説明 |
|------|------|
| **Sync word** | パケットの先頭を示すマジックナンバー（0xCAFEBABE） |
| **Stateless** | ステートレス方式。状態を保持せず、毎回初期化 |
| **Stateful** | ステートフル方式。状態を保持し、継続的に処理 |
| **Internal buffer** | PC側の内部バッファ。150KB容量で2-3パケット分を保持 |
| **Buffer position** | 内部バッファの現在読み取り位置 (buffer_pos) |
| **Action queue** | Spresense側の送信待ちキュー。最大7バッファ |
| **Empty queue** | Spresense側の空きバッファキュー |
| **Sync established** | sync検索が完了し、ステートフル読み取りモードに入ったフラグ |
| **Packet boundary** | パケット境界。TCPはbyte streamなので明示的な境界なし |
| **GS2200M** | Sony Spresense用WiFiモジュール（TCP/IP stack内蔵） |
