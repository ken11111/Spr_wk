## 📋 Phase 7-15 を通した 5 大技術洞察 (エグゼクティブサマリ)

8 ヶ月・9 Phase の分析を通して得られた、本プロジェクトの **設計基盤を形作る 5 つの核心的洞察**。

### 1. TCP 接続安定性は構造的に GS2200M に律速される (Phase 7)
- WiFi 802.11n の能力 (12 Mbps) を引き出せず、**SPI 4 MHz = 500 KB/s が天井**
- 電波環境依存の接続切断は確率的に必発 → 「切断ありき」の設計へ転換
- → Phase 9 自動再接続機構の必要性を確立

### 2. バッファキュー設計が FPS 性能を決定 (Phase 8)
- シングルスレッド → 3 スレッドパイプライン化で **FPS 大幅改善**
- ただしキュー深度動的制御が無いと滞留 → 後の Phase 10 PID 制御の根拠
- → 構造的天井: NuttX IOB プール 1568 B / GS2200M `tx_buff[1]` のシリアライズ

### 3. 自動再接続が逆効果になり得る発見 (Phase 9 → 9.1)
- 直感的には「再接続=回復」だが、**Phase 9.1 で 75.5% フレームドロップ** が観測 (CRITICAL_ISSUES.md)
- GS2200M の RST 拒否パターンで再接続が連鎖崩壊
- → ADR-002 v1.1 で自動再接続戦略を全面改訂

### 4. TCP 健全性監視で予兆検出が可能 (Phase 9.2)
- RTT / retransmit / send 時間 etc. を統合した健全性スコアで **切断前の劣化** を検出
- 予防的再接続: 30 秒の致命的停止 → 3 秒の予防的リセット (-90%)
- → Phase 9.2 の中核アーキテクチャに反映

### 5. 構造的天井は Tier 移行でしか緩和できない (Phase 15)
- V4L2 buffer count 固定 3 / USB CDC-ACM 律速 / SPI 帯域 500 KB/s ピーク
- ソフトウェア最適化の限界を定量化 → **Full HD 30 fps は物理的達成不可** (要求書 Q1 で確定)
- → Tier 2/3 移行 (ADR-006 GATE-1) が根治の必要条件

### 2.2 Phase 8 重要発見

#### 🎯 GS2200M特有挙動特定

**発見1: 内部バッファ制約**
```yaml
制約内容:
  送信バッファ: 2KB固定サイズ
  受信バッファ: 1KB固定サイズ
  フラグメント: 大きなパケット分割必要

影響:
  高速転送時: バッファオーバーフロー頻発
  大容量データ: MJPEG転送で制約顕在化
  回避策: 小分け送信・フロー制御必要
```

**発見2: タイムアウト特性**
```yaml
デフォルトタイムアウト:
  接続確立: 10秒
  データ送信: 5秒
  応答待機: 3秒
  Keep-alive: 30秒

最適化結果:
  Keep-alive短縮: 30秒→10秒
  送信タイムアウト: 5秒→2秒
  再送間隔: 3秒→1秒
  効果: 早期切断検知・高速回復
```

**発見3: 環境依存切断パターン**
```yaml
パターン1: 電波劣化切断
  発生条件: RSSI < -75dBm
  予兆時間: 5-10秒前から劣化開始
  対策: RSSI監視・位置調整

パターン2: 干渉起因切断
  発生条件: 2.4GHz帯域競合
  特徴: 間欠的・不定期発生
  対策: チャンネル変更・5GHz移行

パターン3: 負荷起因切断
  発生条件: 高速連続データ転送
  特徴: バッファ満杯→タイムアウト
  対策: フロー制御・速度制限
```

### 3.2 Phase 9 アルゴリズム開発

#### 🧠 健全性監視アルゴリズム

**移動平均アルゴリズム**:
```c
// Phase 9で開発・Phase 9.2で実装
typedef struct {
    uint32_t window_size;       // ウィンドウサイズ (デフォルト10)
    uint32_t rtt_samples[20];   // RTTサンプル配列
    uint32_t sample_index;      // 現在インデックス
    uint32_t sample_count;      // サンプル数
    uint32_t moving_average;    // 移動平均値
} moving_average_t;

void update_moving_average(moving_average_t* ma, uint32_t new_rtt) {
    // サンプル追加
    ma->rtt_samples[ma->sample_index] = new_rtt;
    ma->sample_index = (ma->sample_index + 1) % ma->window_size;

    if (ma->sample_count < ma->window_size) {
        ma->sample_count++;
    }

    // 移動平均計算
    uint32_t sum = 0;
    for (int i = 0; i < ma->sample_count; i++) {
        sum += ma->rtt_samples[i];
    }
    ma->moving_average = sum / ma->sample_count;
}
```

**スパイク検出アルゴリズム**:
```c
// スパイク検出・カウント
typedef struct {
    uint32_t baseline_rtt;      // ベースラインRTT
    uint32_t spike_threshold;   // スパイク閾値 (ベースライン×1.5)
    uint32_t spike_count;       // スパイク累積数
    uint32_t recent_spikes;     // 最近のスパイク (1分間)
} spike_detector_t;

bool detect_rtt_spike(spike_detector_t* detector, uint32_t current_rtt) {
    bool is_spike = (current_rtt > detector->spike_threshold);

    if (is_spike) {
        detector->spike_count++;
        detector->recent_spikes++;

        // スパイク頻発チェック (1分間に5回以上)
        if (detector->recent_spikes >= 5) {
            return true; // 再接続トリガー
        }
    }

    return false;
}
```

**健全性スコア算出**:
```c
// 統合健全性スコア (0-100)
uint8_t calculate_health_score(
    uint32_t current_rtt,
    uint32_t baseline_rtt,
    uint32_t recent_spikes,
    uint32_t packet_loss_rate
) {
    uint8_t rtt_score = 100;
    uint8_t spike_score = 100;
    uint8_t loss_score = 100;

    // RTT評価 (50%重み)
    if (current_rtt > baseline_rtt * 2) {
        rtt_score = 30; // 大幅劣化
    } else if (current_rtt > baseline_rtt * 1.5) {
        rtt_score = 60; // 軽微劣化
    }

    // スパイク評価 (30%重み)
    spike_score = max(0, 100 - recent_spikes * 20);

    // パケット損失評価 (20%重み)
    loss_score = max(0, 100 - packet_loss_rate * 5);

    // 重み付け統合
    uint8_t health_score = (rtt_score * 50 + spike_score * 30 + loss_score * 20) / 100;

    return health_score;
}
```

### 3.3 Phase 9 実装パターン確立

#### 🏗️ 再接続アーキテクチャ

**状態マシン設計**:
```yaml
状態定義:
  CONNECTED: 正常接続状態
  DEGRADED: 劣化検知状態
  RECONNECTING: 再接続実行状態
  FAILED: 再接続失敗状態

遷移条件:
  CONNECTED → DEGRADED: 健全性スコア < 70
  DEGRADED → RECONNECTING: 継続劣化・閾値下回り
  RECONNECTING → CONNECTED: 再接続成功
  RECONNECTING → FAILED: 再接続タイムアウト
  FAILED → RECONNECTING: 自動リトライ

タイムアウト:
  劣化判定猶予: 3秒
  再接続実行: 3秒以内
  失敗リトライ: 10秒間隔
```

**マルチスレッド協調**:
```c
// Phase 9設計・Phase 9.2実装
typedef struct {
    pthread_t monitor_thread;    // 健全性監視スレッド
    pthread_t camera_thread;     // カメラキャプチャスレッド
    pthread_t comm_thread;       // 通信スレッド

    shared_health_data_t health; // 共有健全性データ
    pthread_mutex_t health_mutex; // 健全性データミューテックス

    reconnect_state_t state;     // 再接続状態
    bool reconnect_requested;    // 再接続要求フラグ
} integrated_system_t;

// 健全性監視スレッド (100ms間隔)
void* health_monitor_thread(void* arg) {
    integrated_system_t* system = (integrated_system_t*)arg;

    while (system->running) {
        // RTT測定・健全性評価
        uint8_t health_score = measure_and_calculate_health();

        // 再接続判定
        if (health_score < RECONNECT_THRESHOLD) {
            pthread_mutex_lock(&system->health_mutex);
            system->reconnect_requested = true;
            pthread_mutex_unlock(&system->health_mutex);
        }

        usleep(100 * 1000); // 100ms待機
    }
}
```
